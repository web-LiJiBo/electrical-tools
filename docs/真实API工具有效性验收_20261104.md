# 真实API调用下的工具有效性验收

日期：2026-11-04。代码基准：`b1ea1ab0708ce9d43c62c585d96a10874a6eb003`。

## 结论

真实大模型接入后的核心链路可以运行：问题分解、真实库内检索、建议生成、通用模板转换，以及明确的模拟下发和反馈均有成功案例。但工具对部分问题的理解、适用性判断和回答状态仍不可靠，不能因为API调用成功就认定所有用户问题已经正确处理。

本轮使用实际外部API，不使用受控假响应或离线分解器作为验收依据。用户授权的“由助手代替大模型生成中间内容”没有启用，因为22次实际模型调用全部成功。

- 补齐项目虚拟环境的CPU版PyTorch与NumPy，实际加载`TorchAttentionClassifier`，响应中的一致性模型标识为`lunwen-attention-model`。
- 按`configs/settings.example.yaml`在线配置装配全部53140个来源记录：6674个原核验库、46466个补充库，未跳过文件；共58316条规则。

- 本地HTTP验收服务使用127.0.0.1:8001，按产品原有路由调用`/analyze`、`/decompose`及模拟预览/执行接口。
- 审计与模拟事件写入本次`.tmp/online_validation_20261104`目录，避免混入日常运行记录。原配置仅在临时副本中改了审计输出路径，模型、检索参数和数据范围保持原配置。
- GitHub接口确认仓库公开，并确认b1ea1ab公开提交的树。运行前逐文件核验53140个来源的Git哈希，排除未跟踪、已修改来源及用户自定义模板。外部模型只收到测试问句、每次最多5条检索到的公开条款和项目虚拟设备状态，未上传完整标准库。
- 密钥只用于配置的大模型接口认证，没有写入报告、请求提示词或结果文件。

## 已跑通的有效流程

### 1. 标准问答与检索

问题：“空气压缩机能效试验的吸气温度应在什么范围内？”

指定标准/章条，以及不指定来源的两个请求，均通过真实分解和建议API返回库内`GB 19153-2019`第6.2条的5℃～40℃范围。无来源提示时，模型还区分了20℃规定工况与允许测量范围，没有把二者混成同一条件。这些数值是本轮工具检索结果，不代表本报告另行核验标准现行状态。

问题：“请按2099版标准说明变压器的温升限值。”

实际返回`uncertain`、无来源证据，没有降用其他版本。此请求真实调用分解API，因缺少来源，没有继续调用建议API。

### 2. 主变正常和高温工况

同一句“主变1目前温升状态是否正常？请列出判断依据和建议”，分别在正常、高温模拟工况下运行：

| 工况 | 实际热点/顶层油/平均温升 | 结果 |
| --- | --- | --- |
| 正常 | 50/40/45 K | 结构化比对normal，模型说明三项未越限 |
| 高温 | 85/65/70 K | 结构化比对abnormal，模型说明三项越限 |

两次均真实调用分解和建议。模型没有把越限直接解释为跳闸授权，并指出来源编号/版次不全、不同条款限值存在差异。因而这一流程在演示参数比对层面有效，正式适用性仍未闭合。

### 3. 用户假设工况的真实模型表现

问题给定热点95K、顶层油45K、平均45K，并要求按这些输入分析。

本轮大模型明确识别了95K假设与50K当前快照的区别，并解释若假设成立，热点95K超过所引78K，而其他两项未超过相应限值。不能继续沿用先前离线结果，声称“在线模型也完全忽略了用户输入”。

但`device_assessment.status`仍为normal，checks仍使用50/40/45 K，表示当前快照比对。工具没有独立给出用户假设工况的结构化结果。文字和字段各自描述不同对象，下游若只读normal会误解本次提问结论。应为“当前快照比对”和“假设工况比对”分别标明数据来源、实际参与值及结论。

### 4. 真实模型建议到模拟执行的完整链路

问题：“依据标准，模拟换流阀1的阀出水温度保护动作后，应如何处理？请给出模拟操作建议。”

实际流程：

1. 真实大模型完成分解，完整标准库检索召回包括`1626_clause2:rule:1`在内的来源。
2. 真实建议API提出`runback_power`，参数`target_power_mw=80`，并引用检索来源。
3. 模型明确80MW来自设备已配置回降目标，未把它编成标准限值；阀出水保护动作、回降允许、未执行回降及直流未闭锁等条件由模板校验。
4. 工具生成模拟协议预览；此时状态仍为100MW。
5. 明确调用模拟执行后，功率100→80MW，`dc_blocked=0`，反馈为`succeeded`。
6. 重复提交同一命令返回相同结果，未重复改变状态。

该案例证明“真实API→检索→建议→模板→模拟执行反馈”可运行，不代表来源已经完成标准身份和现场适用性核验，也不代表接入了真实设备。

另对明确的风机启动验证：执行后具体业务场景和自动汇总视图都显示运行，重复提交返回相同结果。这个风机直接操作入口本身未调用模型，应与上面的真实模型建议链路分开计数。

## 在线模式仍存在的问题

### A. 部分自然语言入口根本没有调用模型

| 问题 | 在线实测结果 |
| --- | --- |
| 主变99当前状态如何？ | 回答主变1、2数据，未提示99不存在 |
| 比较主变1和断路器2的当前状态 | 返回断路器1、2，遗漏主变1 |
| 热点超过80K才启动风机 | 当前50K仍生成可模拟下发的立即启动预览，条件丢失 |
| 将调压装置设定为8.5档 | 生成5档预览 |
| 禁止启动主变1的冷却风机 | 生成启动预览 |
| 主变1的冷却风机启动了吗？ | 生成启动预览 |

以上均通过正在运行的在线服务复现；实际模型调用记录为0。根因在`application/analysis_pipeline.py:82`优先进入`simulation_query`，以及后者的目标、动作、数值和排除词规则。不能把这些错误归因于大模型响应不正确。

另通过产品`/decompose`接口对三个相同问题直接调用真实大模型，作为对照：

- 条件式问题正确返回热点温升`>80 K`约束。
- 并列比较正确保留“主变1”和“断路器2”两个实体。
- 未知设备问题保留“主变99”，未替换成已存在设备。

这证明工具原生处理没有使用这些中间结果。修正时应让所有入口遵守相同的设备身份、否定/疑问、条件和数值约束；使用模型解析也必须经过设备目录和可执行条件验证。

### B. 模型指出条款不适用，工具仍将其作为答案保留

问题：“手机如何恢复出厂设置？”

实际检索选中会议纪律中的“不得玩手机”等条款。真实大模型明确说这些来源不适用、不能提供该问题的操作步骤，但工具仍把原始会议纪律附在回答末尾，保留`selected_rule`和`answered`。

问题：“请根据标准分析主变1冷却风机的启动条件，并给出操作建议。”

实际召回的是应急响应启动程序。真实大模型指出它们与冷却风机启动无直接适用关系，未生成设备指令；工具仍保留这些条款为采用来源，并标记answered。

根因包括检索对“启动”等共有词的相关性判断、`grounded_advice.py:98`把建议与旧来源回答拼接，以及`analysis_pipeline.py:_respond`没有把来源不支持反馈转为统一的结论状态。修正不能仅依赖搜索模型文字里的“无关”关键词，应在建议契约中结构化表达逐条支持关系、适用性不足和无法回答原因，再统一决定采用来源及返回状态。

### C. 来源身份和适用性数据仍不足

本轮主变和换流阀检索来源中存在“未标注标准”、版次和章条缺失，也出现不同来源的温升限值差异。模型已主动提醒这些缺口，工具尚不能替代完整来源核验。

应优先补齐当前演示涉及条款的正式编号、名称、版次、章条、设备类型、冷却方式及完整适用前提，并保留原文与审查记录。仅补更多同类条款，可能进一步放大相似内容竞争和版本混用。

### D. 总耗时主要不能只看模型请求

正常主变请求总耗时34.147秒，两次模型调用合计5.703秒，其余环节约28.444秒；换流阀建议请求总耗时37.417秒，模型合计5.971秒，其余约31.446秒。

说明当前本地处理开销值得单独分析。下一轮应分段记录实体链接、规则召回、排序、一致性与来源评估用时，再决定索引和缓存策略；本轮未据总耗时直接断言某个内部函数占用了全部时间。

## 建议的本地修正顺序

1. 统一所有问句入口的意图、目标和条件约束，修正未知编号、并列对象、否定疑问及档位解析；新增测试应同时在真实在线服务验收。
2. 把“所引条款能否支持回答”加入结构化建议和结果合并，删除无关的采用来源，统一`answered/uncertain`与回答、证据的语义。
3. 分开当前模拟状态与用户假设评估的结构化结果，明确数据来源。
4. 补齐演示来源身份与适用条件，随后按实际分段耗时优化检索与评估。
