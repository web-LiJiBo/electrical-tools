## 调整后的流程

默认在线模式：

用户自然语言问题 → DeepSeek结构化理解 → 后端核对设备、动作和条件 → 查询状态或检索条款 → 必要时调用建议模型 → 后端校验及模拟预览 → 用户明确下发 → 状态和反馈。

- `/analyze`及复用分析流程的生成、校验和报告入口均先完成一次模型理解，不再让模拟关键词分支提前返回。
- API以`scenario.query_kind`给出状态、能力、标准咨询、评估、操作或其他问题类型；其动作、约束、设备实体与上下文继续传给后续处理。
- 主变条款评估复用本次分解，不再为同一问题重复调用分解。需要条款梳理或建议时仍保留独立的建议调用。
- 当前状态、设备身份、动作模板、协议映射、联锁与执行版本来自后端。API不直接提供执行授权或改写设备事实。

## DeepSeek结构化理解的输出

理解模型输出单个JSON对象：`intent`（处理意图）、`entities`（设备及参数实体）、`actions`（标准动作码）、`constraints`（参数、比较符、值、单位和条件）、`standard_refs`（标准编号和版次）、`scenario`（场景与问题类型）、`keywords`及`confidence`。设备名称仍需后端目录匹配，模型置信度不代表业务准确率。

`scenario.query_kind`区分当前状态、可用动作、标准咨询、评估、具体操作和其他问题。例如“主变1的冷却风机启动了吗？”即使提取出`start`，其`query_kind=device_status`仍导向状态查询；“请让主变1的冷却风机开始转动”才按操作意图继续校验和生成预览。

## 本批修正

1. 在线理解失败、输出缺少问题类型时显式返回模型处理未完成，不静默用本地规则生成操作。关闭建议模型不会自动允许理解降级。
2. 关键词保留为辅助检查；否定、疑问、条件和多步骤限制不能被模型误分类绕过。共享保护同时覆盖直接模拟预览和检索后的模型建议转换。
3. 已识别但尚未编译为执行前校验的用户条件，包括负责人确认等自然语言条件，明确阻止无条件预览。此阶段没有实现通用条件指令或自动操作序列。
4. 区分并列设备与局部所属短语，未知编号不替换为同类已有设备；混合出现已知、未知编号时不只选已知目标继续操作。
5. 模型解析的上下文设备可用于状态、评估和建议的目标核对，仍要求匹配当前场景目录。
6. 档位保留完整数值，非法小数或负值不会截取成另一合法整数。目标等值赋值与当前档位比较条件分开处理；兼容API实际使用的“档位”“目标档位”“调压档位”等参数名称。
7. 对API已知的同义意图字段做结构规范化，例如`assessment`对应`compliance`；未知分类继续报错，不补造业务内容。建议提示词与接口的最多5项建议限制保持一致。
8. 首页模型失败状态统一表述为“模型处理未完成”。
