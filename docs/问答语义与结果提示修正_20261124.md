# 问答语义与结果提示修正

开始日期：2026-11-24；完成验证：2026-11-25。已随2026-11-25统一更新发布；以下为本地验证记录。

## 本次问题及处理

1. **并列操作误走顺序流程**：原先只有`order`编号，后台能确认顺序执行机制可用，但不能确认编号有无原文依据。本次为顺序增加独立原文证据，区分清单列举与真实执行依赖，首轮识别、条款建议桥接、规范化及独立复核保持同一份依据。不存在本次原文依据的顺序不进入顺序预览；也不擅自删除可能真实存在的依赖。常规独立操作保持兼容，不为每次问答新增模型调用。
2. **整批状态容易误读**：展示每批可预览、受阻和待澄清数量；真实顺序流程说明当前开放步骤，未开放的后续草案不算成功预览。
3. **补充状态与执行动作容易混淆**：保留用户补充当前值优先于模拟预设的规则，明确提示补充值已更新当前模拟会话；生成指令本身尚未执行。详细原值、采用值及来源继续放在系统理解中，避免堆长回答。

此前储能停止后有功未归零的问题已在默认模板补齐，本次保留其回归检查，不重复修改已修复逻辑。

组合验证进一步发现并修正：业务参数里的设备许可不作为整批语义批准条件，改由后台逐项检查；“逆变器／储能”简称关联同句前文唯一同类型设备，多个同类型候选仍须澄清；模型总判定与逐项结果矛盾时不擅自通过，最多重核一次，仍矛盾返回复核失败。条款桥接兼容旧版未提供新证据字段的独立动作；有序动作缺少本次原文不能通过证据校验。

## 验证原则

业务验收使用已配置的真实DeepSeek Flash API，不使用模型替身。采用原失败句及两道新组合问题，分别覆盖并列关系、多设备多动作、单位换算、部分生成、状态查询、用户补参、成功反馈依赖和生成不执行。结构契约与页面显示另作组件检查，不把组件通过记为真实模型理解通过。

最终16项后端边界与状态检查、25项前端组件检查通过。Chrome使用真实API返回验证页面：部分成功显示“1项可预览，1项受阻/待澄清”，回答页显示补充值已更新会话；顺序草案与当前开放预览分开显示。
