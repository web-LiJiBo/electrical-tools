1: 项目解读
2: 机器可读标准知识服务
3: 面向新型电力系统的标准检索、推理、验证与候选指令生成后台
4: 一句话定位：把供人阅读的电力标准，转化为业务系统能够检索、推理、验证和追溯的机器可读知识；系统只生成候选建议，不直接控制设备。
5: 1. 项目是干什么的
6: 本项目是一套纯后台的机器可读标准知识服务原型。它接收自然语言业务问题，从已结构化的标准条款中寻找依据，形成带证据的判断，并在条件允许时生成 IEC 61850 或 Modbus 候选指令。
7: 它并不是普通的“大模型问答”。大模型主要负责理解查询；最终结果还要经过本地数据检索、候选规则评价、语义转换、多层验证与安全门禁。
8: 2. 它要解决的问题
9: 传统电力标准多以 Excel、PDF 或文本存在。人能够阅读，但业务系统难以直接回答以下问题：
10: 某项条款适用于什么场景、设备和运行条件？
11: 条款要求执行什么动作，数值阈值和约束是什么？
12: 当前业务事实是否满足规则，结论是否存在冲突？
13: 判断依据来自哪项标准、哪个版本、哪条条款？
14: 标准要求如何映射为设备协议层面的候选操作？
15: 因此，项目的本质是建立一条从“标准文档”到“可执行语义”的受控转换链路。
16: 3. 端到端处理流程
17: 1
18: 查询分解
19: 本地 Qwen 提取意图、实体、动作、标准号、场景和数值约束；模型不可用或输出不合格时，回退到保守的原文抽取。
20: 2
21: 场景建模
22: 构建海上风电等场景上下文，将用户参数合并进业务事实，并识别设备类型、协议映射等缺失字段。
23: 3
24: 实体与规则检索
25: 对结构化标准 JSON 进行实体链接、规则召回和证据重排，保留候选排名及评分。
26: 4
27: 候选综合评价
28: 结合检索分数、一致性特征和混合推理结果，从 Top-K 规则中选择最终条款。
29: 5
30: 语义与中间规则
31: 将条款规则转换成主体、动作、对象、条件、约束等语义元组，并编译为 ILR/SWRL 表达。
32: 6
33: 候选指令生成
34: 根据场景、动作、设备配置和目标协议匹配模板，生成 IEC 61850 或 Modbus 候选载荷。
35: 7
36: 验证与安全门禁
37: 验证适用性、语义、条款与指令一致性、协议合法性和逻辑正确性；任何结果均禁止自动下发。
38: 8
39: 报告与审计
40: 输出事实报告、条款原文证据、警告、缺失字段和请求级审计记录。
41: 4. 核心模块
42: 模块
43: 职责
44: decomposition
45: 本地 Qwen 查询分解、Schema 校验、术语与单位归一化、失败回退。
46: scenarios
47: 场景识别、上下文构建、业务参数合并和缺失字段判断。
48: retrieval_engine
49: 读取结构化条款，完成实体链接、规则召回、排序和证据构建。
50: knowledge_graph
51: 构建 Document、Entity、Rule 节点及关系，支持内存或可选 Neo4j。
52: consistency_evaluation
53: 计算文本、结构、规则集合与数值约束的一致性特征。
54: hybrid_reasoning
55: 融合安全规则求值、业务事实、图谱路径和一致性判断。
56: instruction_engine
57: 抽取语义元组，生成 ILR/SWRL，并适配 IEC 61850、Modbus。
58: validation
59: 适用性、语义、条款—指令、协议、逻辑、冲突与安全校验。
60: reporting / audit
61: 生成基于证据的报告，记录请求、输入、输出和场景。
62: feedback
63: 收集业务反馈并形成待审批的优化建议，不自动改变生产行为。
64: application / api
65: 编排完整分析链路，提供命令行和 FastAPI HTTP 接口。

92: 6. 输入、输出与接口
93: 6.1 最小输入
94: 主入口只要求 query。scenario_hint、业务参数、目标协议以及对话上下文均为可选；生成协议候选指令时，通常还需要 device_config。
95: 字段
96: 作用
97: query
98: 自然语言问题或业务场景描述，必填。
99: scenario_hint
100: 可选场景提示，例如“海上风电”。
101: parameters
102: 设备、运行状态、电压等级、测量值及 device_config。
103: target_protocol
104: IEC61850 或 Modbus；缺省时根据配置和模板选择。
105: conversation_context
106: 可选的上下文消息，用于查询分解。
107: 6.2 分析输出
108: 查询分解结果、场景上下文和缺失字段；
109: 命中的实体、候选规则、排名和综合评分；
110: 最终条款、标准原文证据及支持状态；
111: 一致性评价、推理状态和推理路径；
112: 语义元组、ILR 及协议候选指令；
113: 多层验证结果、警告、事实报告和审计记录。
114: 6.3 HTTP API
115: 接口
116: 用途
117: GET /health
118: 健康检查，同时声明禁止设备下发。
119: POST /analyze
120: 执行完整端到端分析，是系统的主要入口。
121: POST /decompose
122: 只执行查询分解。
123: POST /search
124: 执行实体链接和规则检索。
125: POST /generate-instruction
126: 返回完整分析中的候选指令部分。
127: POST /validate
128: 返回验证状态和证据。
129: POST /generate-report
130: 返回结构化事实报告。
131: GET /audit/{request_id}
132: 按请求编号获取审计记录。
133: 7. 状态与安全边界
134: 状态
135: 含义
136: needs_human
137: 验证完成，但必须人工确认。这是配置完整时的正常成功状态。
138: uncertain
139: 证据、业务事实、场景适用性或协议配置不足，不能可靠判断。
140: fail
141: 条款不适用、语义冲突、协议不合法或逻辑校验失败。
142: 关键安全原则：所有 CandidateInstruction 的 dispatch_allowed 均为 false。即使每层验证通过，安全门禁也只返回 needs_human，不允许直接下发到真实设备。
143: 8. 当前成熟度判断
144: 从代码结构、数据、测试和构图产物来看，该项目已经是端到端可运行的后台原型：主流程、HTTP API、数据检索、规则选择、候选指令、验证、报告和审计均已接通；最近保存的标准测试流程状态为 passed。
145: 但它仍然属于科研成果工程化与交付验证阶段，而不是生产控制平台。
146: 默认依赖本地 JSON 和内存图谱，Neo4j 属于可选后端。
147: 尚未接入真实数据库、调度平台或现场设备。
148: 完整效果依赖本地 Qwen、SBERT 和一致性模型的可用性。
149: 真实 Qwen 推理内存开销较高，未纳入普通一键测试。
150: 部分细分 API 会复用并重新执行完整分析链路，服务边界仍可进一步细化。
151: 所有设备操作都只是候选建议，人工确认是不可绕过的产品边界。
152: 9. 总结
153: 这个项目连接了标准文档与业务系统：上游将标准条款结构化为实体、规则和约束；中间层通过检索、一致性评价和混合推理形成有依据的判断；下游将判断映射成可验证、可追溯但不可自动执行的协议候选指令。
154: 它最有价值的地方不在于“回答一句话”，而在于让每个结论都能回到具体条款、具体证据、具体验证过程和具体安全状态。
